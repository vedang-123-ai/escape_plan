S6.1 — Schema 2.0: household facts, sensory tags, safety objects · ~5h · Prereqs: none (blocks S6.3, S6.4, S6.5)

Context: the readiness pivot needs four things the contract cannot currently express — who the
household is beyond routing tags, where the utility shutoffs are, which room is the storm safe
room, and whether a piece of furniture has been secured. This is the one session in the S6 arc
permitted to touch `schema/homemodel.schema.json`, and it is a `schema_version` bump (1.1 → 2.0)
with the sign-off the project's rules require. Everything else in the arc is blocked on it.

---

```
Read CLAUDE.md, docs/playbook/06-pivot-intro.md, docs/decisions.md, and
.claude/rules/paths/schema.md before writing anything.

MISSION
Bump the HomeModel contract from schema_version "1.1" to "2.0" to support the readiness pivot,
and keep the JSON Schema, the pydantic models, and the Swift Codable structs in exact lockstep.
This is the blocking session for the entire S6 arc — S6.3, S6.4 and S6.5 all wait on it.

WHY THIS IS DELICATE
schema/homemodel.schema.json is the project's one law. It is consumed by the scan converter, the
editor reducer, the routing engine, the agent, and the renderer. A PreToolUse hook will ask you to
confirm before you edit it — that prompt is the process working, not an obstacle. Every fixture in
schema/fixtures/ and every round-trip test must still pass when you are done.

WHAT TO ADD (and nothing else)

1. Profile tags — extend the `profile.tags` enum with `hearing_impaired` and `vision_impaired`.
   docs/profile-constraint-mappings.md currently documents hearing_impaired as deliberately NOT
   mapped, because it is alarm guidance rather than routing guidance. That reasoning still holds:
   add the tags to the contract, and leave them producing ZERO routing constraints. They exist so
   the S6.4 checklist can act on them (strobe alarms, bed-shakers). Update that doc's "Not mapped,
   deliberately" section to say they are now expressible but still routing-neutral, and keep the
   test that asserts they change no edge.

2. A household facts object — new top-level optional `household` with:
   - `tenure`: "rent" | "own" | null (null = not answered; skipping is always allowed)
   - `existing_equipment`: array of "smoke_alarm" | "co_detector" | "extinguisher" | "generator",
     uniqueItems, default []
   It is optional on purpose: every pre-2.0 document must still load without one.

3. Safety points — new per-floor `safety_points` array. Each entry:
   - `id` (unique, may not be "EXTERIOR"), `kind`: "gas_shutoff" | "water_shutoff" |
     "electrical_panel", `position` ($ref point, floor-local meters), `source`, `confidence`
   Follow the existing `object` def's precedent exactly: NO room_id — containment is derived
   geometrically so moving a room can never dangle a reference.

4. Secured-furniture flag — add optional `secured` (boolean, default false) to the `object` def.
   Earthquake mitigation needs to record that a wardrobe has been strapped. Routing must continue
   to ignore it completely: an obstacle is an obstacle whether or not it is bolted down.

5. Scan freshness — add optional `last_scanned` (ISO 8601 date-time, nullable) to `meta`.
   S6.6 drives the rescan nudge off it. Null means "never scanned / hand-built".

DELIBERATELY NOT IN THIS SESSION
- No `safe_room` field. The storm safe room is COMPUTED by the S6.3 engine from geometry, and
  caching a computed value in the contract invites it to go stale against the model it derives
  from. If S6.3 later proves it needs persistence, that is a separate, argued change.
- No checklist state. `ChecklistState` already persists id→done via the iOS app; do not move it
  into the schema.
- No hazard/peril enum in the schema. Perils are an engine concept, not a document concept.

LOCKSTEP REQUIREMENTS (a change is incomplete until all four agree)
- schema/homemodel.schema.json — draft 2020-12, `additionalProperties: false` preserved everywhere,
  every new field described in the same voice as its neighbours (say WHY, not just what).
- backend/app/models.py — pydantic v2, fully typed. Validation invariants live here, not only in
  the schema: safety_point ids unique across the home, positions finite, tenure/equipment enums.
- The Swift Codable structs under escape_plan/Models/ — field names and optionality mirrored exactly.
- schema/fixtures/ — bungalow, apartment, twostory, jagged all bumped to "2.0" and still valid.
  Seed the fixtures with realistic new data: give twostory a gas shutoff and an electrical panel,
  give at least one fixture a `secured: true` wardrobe, give one a `household` with tenure "rent"
  so S6.4 has a renter case to test against. Keep the deliberately-plantable safety problems that
  the S3.2 agent tests assert on — do not "fix" the single-exit apartment or the small egress window.

BACKWARD COMPATIBILITY
Decide and document one of: (a) loader accepts 1.1 documents and migrates them in memory, or
(b) a one-shot migration on open. Recommend (a) — every new field is optional, so a 1.1 document is
a valid 2.0 document with the new fields absent, and the only real work is the version string. Do
not silently rewrite a user's file on disk without a save.

ACCEPTANCE
- `python3 -m pytest backend/tests/ -m "not live"` green, including new model-validation tests for
  every invariant you added (duplicate safety_point id rejected, unknown tenure rejected, etc).
- `swift test --package-path tools/editorcore` green.
- The Swift decode → encode → semantic-compare round-trip test passes on all four 2.0 fixtures.
- xcodebuild test green (re-run once before believing a red; true counts come from
  `xcrun xcresulttool get test-results summary --path <bundle>`, not the console tail).
- `python3 backend/corpus/validate.py` still exits 0.
- A 1.1 document still loads.
- Run the schema-contract-guardian agent and act on what it finds.

CLOSE OUT
Update docs/tracker/TODO.md (S6.1 done, unblock S6.3/S6.4/S6.5), write docs/tracker/notes/<date>-s6-1-schema-2-0.md
from _TEMPLATE.md, and add a docs/decisions.md entry explaining the 2.0 bump: what was added, what
was deliberately left out (safe_room, checklist state), and the backward-compatibility ruling.
```
