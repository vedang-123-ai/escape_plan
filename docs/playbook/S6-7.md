S6.7 — Composite readiness score across three perils · ~5h · Prereqs: S6.3, S6.4

Context: the score is the pivot's portable artefact — the number a user could hand an insurer, and
the number the responder snapshot carries. It already exists as a pure, hand-reproducible 0–100 for
fire. This session widens it to three perils without losing the property that makes it defensible:
a reviewer can recompute any score by hand from a documented weights table.

---

```
Read CLAUDE.md, docs/playbook/06-pivot-intro.md, docs/preparedness-score-weights.md, and
.claude/rules/languages/python.md. Then read backend/app/scoring/score.py and
backend/app/scoring/checklist.py in full.

MISSION
Extend the preparedness score into three per-peril sub-scores (fire, earthquake, severe weather)
plus one composite headline number, keeping every point arithmetic over facts the deterministic
engine established.

THE PROPERTY YOU MUST NOT LOSE
score.py's acceptance bar today is that docs/preparedness-score-weights.md and the constants stay
in lockstep, so a reviewer can reproduce any score by hand. Widening to three perils multiplies the
ways that can rot. Keep the doc and the code in lockstep in the same commit, and add a test that
fails if a weight exists in code but not in the doc's table (or vice versa) if you can express it
cheaply — a hand-maintained correspondence has already drifted once in this repo's history.

DESIGN

1. Sub-scores: each peril scores 0–100 over the items tagged for it plus the findings that peril's
   engine objective produced. An item tagged "general" contributes to every peril's sub-score —
   mapping your house genuinely helps all three, and pretending otherwise makes the fire score
   drop for reasons a user cannot see.

2. Composite: a documented, explicit combination of the three. Decide and defend the rule. The
   recommendation is a weighted mean where the LOWEST sub-score is weighted more heavily than the
   others, because readiness does not average — a household perfectly prepared for fire and
   defenceless against a tornado is not "70% ready," and a plain mean would let a user grind the
   easy peril to hide the dangerous one. Whatever you choose, write down why in the weights doc,
   and make the breakdown UI show the sub-scores so the composite is never a black box.

3. High-severity findings (no_viable_route, no_viable_safe_room) must be capable of holding the
   composite down no matter how many boxes are ticked. A house where a wheelchair user cannot get
   out should not be able to reach a reassuring number by assembling a supply kit. Cap the
   composite while an unresolved high-severity finding exists, and say so in the UI when it bites.

4. Recurring items (drills, rescan) count as done while inside their interval and re-open after.
   The rescan item specifically MUST NOT reduce the score when it lapses (S6.6's non-punitive
   ruling) — it flags staleness, it does not punish. Encode that here so the two screens agree.

5. AI recommendations stay non-scoring, exactly as today: the AI advises, it never moves the number.
   That separation is a load-bearing part of the "not a wrapper" answer — do not weaken it.

API
Extend the /score response with the three sub-scores and the composite, additively. Existing
consumers must keep working; ScoreScreen's current breakdown rendering should degrade gracefully
if a field is missing rather than crash.

iOS
Update ScoreScreen to show the composite headline with the three sub-scores beneath it, and make
the "what is dragging this down" answer obvious — the single largest deduction should be visible
without tapping anything. Keep the ring/gauge in Theme.swift's semantic scale; no new colours.
The Home tab header (S6.6) reads the composite.

ACCEPTANCE
- Hand-recompute two fixtures' composites from the weights doc alone and match the code's output.
  Put both worked examples in the doc — they are the regression test a human can run.
- A fixture with an unresolved no_viable_route cannot reach a high composite regardless of ticks.
- Lapsed rescan changes no number, only a flag.
- Same inputs → same score, byte for byte (determinism test).
- `python3 -m pytest backend/tests/ -m "not live"` green; xcodebuild test green (re-run a red once).

CLOSE OUT
Update docs/preparedness-score-weights.md with the full three-peril table, the composite rule and
its justification, and the two worked examples. Then docs/tracker/TODO.md, the session note, and a
docs/decisions.md entry recording the composite rule you chose and the alternatives you rejected.
```
