Context: this is the session that has to survive the judge question "did the AI decide what I
should do?" The answer must be the same one S3.4 already gives about routing: no — a fixed,

```
Read CLAUDE.md, docs/playbook/06-pivot-intro.md, docs/profile-constraint-mappings.md (this session
mirrors its structure and its honesty), and .claude/rules/languages/python.md.
Then read backend/app/scoring/checklist.py IN FULL before writing anything.

MISSION
Extend the existing deterministic checklist generator so it produces a unified, hazard-tagged
readiness checklist driven by (HomeModel + household facts + profile tags + engine findings),
covering fire, earthquake and severe weather.

DO NOT REBUILD WHAT EXISTS
backend/app/scoring/checklist.py already generates a deterministic checklist with stable ids,
categories (smoke_alarm, practice, routes, egress, agent_finding, recommendation) and a
ChecklistState (id → done) persisted on the home document by the iOS app. You are EXTENDING that
module, not replacing it. Stable-id discipline is load-bearing: a user's done-state must survive
recomputation, so a given (home, facts, findings) must always produce the same id for the same
item. Add tests that assert id stability across recomputation.

WHAT TO ADD

1. New item categories: `shutoffs`, `safe_room`, `mitigation`, `supply_kit`, `alerts`.

2. A hazard tag on every item: "fire" | "earthquake" | "severe_weather" | "general". Shared work
   is tagged "general" and appears ONCE — mapping the house serves all three perils and must never
   be emitted three times. The unified-list-with-tags shape is a locked decision.

3. The rule table itself — household facts → items. It is a fixed table, pure and total, in the
   same shape as profiles.py's constraints_for_profile. Minimum coverage:
   - `tenure: "rent"` → mitigation items switch to their renter-safe variant (furniture straps
     rather than wall anchors, etc). Same task, different guidance, and the variant text must be
     corpus-cited from S6.2 — if the corpus has no renter-safe line for a task, emit the ordinary
     item rather than improvising a renter version.
   - `existing_equipment` contains "smoke_alarm" → the install-alarms item is pre-satisfied rather
     than emitted as a to-do. Same for co_detector / extinguisher.
   - profile tagged `hearing_impaired` → an alerts item (strobe/bed-shaker alarm, NOAA radio with
     alert), cited. This is where the S6.1 tag finally does work, and it is checklist-only: it
     still produces ZERO routing constraints.
   - profile tagged `mobility_limited` → the sleep-near-an-accessible-exit item the corpus already
     supports, plus escalation of any no_viable_route / no_viable_safe_room finding into a
     high-severity item.
   - profile tagged `child` → accompanied-adult pairing item.
   - `pet` → checklist phrasing only. It must remain a routing no-op; the existing test asserting
     that stays.
   - Any floor lacking a `gas_shutoff` / `electrical_panel` safety point → a "locate and tag your
     shutoffs" item, tagged earthquake+general.
   - Engine findings from S6.3 (no_viable_safe_room, no cover in room X) → items.
   - Unsecured tall/heavy objects (S6.1's `secured` flag false) → earthquake mitigation items.

4. Grounding: every item carries a one-line "why" with a [cite: ...] id that resolves in
   backend/corpus/sources.json. An item with no citable justification does not ship. This is what
   lets S6.6 render a why-line under each row without inventing anything.

5. Recurrence: items like "practice your drill" and "rescan your home" are recurring, not
   one-and-done. Model this as a due-again interval on the item (the corpus supports twice-a-year
   drill practice; the ~6-month rescan cadence is an ENGINEERING CHOICE — label it as one, do not
   attribute it to NFPA). Completion sets a timestamp; the item re-opens when the interval lapses.

PURITY AND SCOPE
- Pure functions, no I/O, no AI, deterministic. Same inputs → same checklist, byte for byte.
- Generation (which items apply) is server-side here. Whether an item is DONE is derived from the
  model where there is a spatial artefact (a gas shutoff exists → that item is satisfied) and from
  stored state only for narrative items (a drill was practiced). Derive first, store only when you
  must — this is what keeps the checklist from drifting from the model.
- Do NOT change the score in this session. S6.7 owns scoring; adding items here will change what
  S6.7 has to weigh, so leave a note for it rather than silently reweighting.

ACCEPTANCE
- On the S6.1 renter fixture, mitigation items come back in renter-safe form; on an owner fixture
  they do not.
- A household with smoke alarms declared does not get told to install smoke alarms.
- A hearing_impaired profile produces an alerts item AND provably no routing constraint change.
- Every emitted item's citation resolves; a test asserts this over the whole generated set for all
  four fixtures.
- Id stability test: recompute twice, ids identical; mutate an unrelated part of the home, the
  surviving items keep their ids.
- `python3 -m pytest backend/tests/ -m "not live"` green; `python3 backend/corpus/validate.py`
  exits 0.

CLOSE OUT
Write docs/household-checklist-mappings.md — the same document profile-constraint-mappings.md is
for routing: every fact → item mapping, the corpus line justifying it, what is deliberately NOT
mapped and why, and any item whose effect is currently a no-op on all fixtures (state it plainly,
with a test, the way the child-penalty no-op is documented today). Then update docs/tracker/TODO.md,
write the session note, and log decisions.
```
