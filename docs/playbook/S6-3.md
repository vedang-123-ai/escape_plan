S6.3 — The peril engine: earthquake cover and storm safe rooms · ~8h · Prereqs: S6.1, S6.2

Context: this is the session that makes the pivot technically real rather than a re-skin. Fire asks
"what is the shortest constrained path to the exterior?" Tornado asks the structural opposite —
"which room is furthest from the exterior, on the lowest floor?" — and earthquake asks a third
question entirely, "what is the nearest sturdy thing to get under, in this room, right now?" Three
objective functions over the same NavGraph, all obeying the same S3.4 profile constraints. If the
demo has one "that is not a wrapper, that is an engine" moment, it is this one.

THE THREE OBJECTIVES

1. FIRE (existing, unchanged) — Dijkstra to the nearest reachable EXTERIOR opening under the
   profile's constraints. Touch it only to factor out anything genuinely shared.

2. TORNADO / SEVERE WEATHER — a shelter search, not an exit search. For each occupant, find the
   best reachable shelter room, where "best" is ordered by, in priority order:
     a. lowest floor available (a basement beats a ground floor beats an upper floor),
     b. fewest exterior-wall adjacencies (an interior room with zero exterior walls wins),
     c. fewest openings to the exterior (windows are the thing you are hiding from),
     d. shortest constrained path from the occupant's origin, as the tiebreak only.
   Derive exterior adjacency from the geometry you already have: a wall segment carrying an
   opening whose room_ids include "EXTERIOR", or a room edge on the footprint boundary. Every
   number you introduce for ordering is an ENGINEERING CONSTANT, not a safety threshold — label it
   as such in code comments exactly the way profiles.py labels stair_penalty_m, and do not
   attribute it to NOAA.
   The path to the shelter obeys the same constraints as any other route: avoid_stairs is still
   hard for mobility_limited, which means a wheelchair user in a house whose only basement access
   is a staircase must NOT be routed there.
   When no qualifying room exists (every room touches an exterior wall — the mobile-home case the
   corpus covers), return a `no_viable_safe_room` finding. This is the tornado twin of
   `no_viable_route` and it is a feature: it tells a family in a mobile home the true answer, which
   per corpus is "leave for a sturdy building." Never downgrade to "best available" and present a
   bad room as a safe room.

3. EARTHQUAKE — two outputs, not one:
   a. Cover points: per room, the nearest sturdy object to get under, searched over floor.objects.
      Only categories that can actually shelter a person qualify (table, and desk-like storage if
      the fixture models it) — a sofa is not cover, a wardrobe is a hazard, not a shelter. Ground
      the qualifying rule in the S6.2 corpus and cite it in the docstring. Rooms with no qualifying
      object return an honest "no cover in this room — drop beside an interior wall away from
      windows" finding IF AND ONLY IF the corpus supports that fallback; otherwise return the
      finding with no alternative rather than improvising one.
      The discredited "triangle of life" must never be produced — add a test asserting the engine
      never recommends standing beside furniture instead of under it.
   b. Post-shaking evacuation: reuse the FIRE exit search verbatim under the same constraints.
      Do not write a second exit search. Earthquake evacuation is fire evacuation with a different
      trigger.

API SURFACE
Extend POST /routes ADDITIVELY, the way S3.4 added profile_id:
  { "home": {...}, "peril": "fire" | "earthquake" | "tornado", "profile_id": "..." }
- `peril` is optional and defaults to "fire", so every pre-S6.3 request behaves identically. A test
  must assert that byte-for-byte.
- `peril` and `profile_id` compose; they are not mutually exclusive.
- The response gains the peril it solved for, so a client can prove which objective drew the paths.
- Unknown peril → 422, never a silent fallback to fire.

PURITY
perils/ is pure-function code: no I/O, no globals, deterministic — same HomeModel in, byte-identical
plan out. The engine and any future agent tool share one implementation. No model is consulted
anywhere in this path; the AI does not compute routes, and it does not compute shelters either.

ACCEPTANCE
- On twostory.json: fire routes to a door; tornado routes the SAME occupant to an interior
  ground-floor room; the two paths are visibly different. That contrast is the demo.
- On a mobility_limited profile whose only shelter is downstairs: no_viable_safe_room, not a
  staircase.
- A fixture with no interior room yields no_viable_safe_room rather than a least-bad guess.
- Earthquake cover search returns a table-type object where one exists and an honest finding where
  none does.
- Determinism test: same input twice → identical output.
- Back-compat test: a /routes request with no `peril` field is identical to pre-S6.3 output.
- `python3 -m pytest backend/tests/ -m "not live"` green.
- Run the grounding-auditor agent: confirm no safety claim in the new code's user-facing strings
  is uncited, and that the AI computes nothing here.
