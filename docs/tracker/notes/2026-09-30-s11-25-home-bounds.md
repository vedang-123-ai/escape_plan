## Decisions / surprises

**The stated budget is 7 s, not the session's example 5 s.** 250,000 cells measures 6.11 s
for a 3-peril `/score` here. 5 s would have meant ~185,000 cells, which rejects a
legitimately scanned 5,000 ft² (460 m²) house. At 250,000 the worst case is ~15–20 s on
Render's free instance — well inside the iOS 90 s timeout, versus *hours* today. Grid
optimisation is explicitly out of scope for this session; if anyone ever scans a mansion,
that is the work to do, not a looser bound.

**Two tests caught two real defects, both mine, both worth recording:**

1. `test_room_grid_cells_at_and_over_the_bound` failed on its first run because the 500 m²
   area cap makes `MAX_ROOM_GRID_CELLS` **unreachable for a rectangle** (90,000 cells is
   900 m² of bounding box). The per-room cell cap exists *only* for slivers, so it is now
   tested with one, and the test says so. A cap you cannot reach is a cap you have not
   tested.
2. `HomeSizeBounds.gridCellCount` **crashed** on a NaN coordinate: `Int(_:)` is a fatal
   error on NaN and infinity in Swift, not a trap-and-return. In the editor that is an app
   crash on a bad scan. It now returns `Int.max` for a non-finite or absurd extent (callers
   read that as "over every bound", which it is), the whole-home sum saturates instead of
   overflowing, and span/cell checks are skipped once any coordinate is non-finite — the
   same place pydantic's `_check_coord` raises. Python was already safe here by accident of
   ordering; Swift was not.

**Non-finite coordinates keep their own message.** `test_safety_point_position_finite` in
`test_models.py` went red when `_check_coord` replaced `SafetyPoint`'s local `isfinite`
check with a range check. The infinity was still rejected, just with "outside the supported
range ±200 m". I kept the specific message instead of relaxing the test: a converter
dividing by zero is a different bug from a house that is too big, and the user-facing
reason should say which.

**The lockstep test reads the Python source.** `testEveryBoundMatchesTheBackendConstant`
parses `MAX_*` out of `backend/app/models.py` and compares all 18 values against
`HomeSizeBounds`, and fails if Python grows a bound Swift does not mirror. A hand-written
mirror that drifts is worse than no mirror — the editor would build homes the server
answers 422 to, and the user would find out at save time. `testCellSizeMatchesTheRoutingEngine`
does the same for `CELL_M` against `nav_grid.py`.

**`Polygon` is ambiguous in a macOS test target.** Quickdraw exports a `Polygon` typedef, so
a local `let poly: Polygon = ...` in a shared test file fails to compile in the SwiftPM
build. Use `[Point]` in test annotations. (Product code is fine — the ambiguity only bites
in explicit local annotations.)

**Measured for S11.26 while I was here, so it does not have to guess.** The largest committed
fixture is only 13,973 bytes, which is a misleading basis for a body limit. The real ceiling is
the largest home S11.25 *accepts*: 8 floors, 200 rooms (3.5 m x 3.5 m each, 245,000 cells),
3,200 openings, 4,000 objects, 800 landmarks, 50 stairs, 50 profiles. Serialised as a `/score`
body that is **1,747,804 bytes (1.7 MiB)** — 125x the largest fixture.

So **a `/score` or `/routes` body limit below ~1.75 MiB would reject a home that pydantic
accepts**, which is a worse failure than no limit: the user would get a 413 for a home the
editor let them build, with nothing to do about it. Either set the compute-route limit at
2 MiB or above, or tighten `MAX_ROOMS` / `MAX_OBJECTS_PER_FLOOR` in the same session so the
two ceilings agree — and say in S11.26's note which was chosen. (A 2 MiB cap is still ~146x
the biggest real body, so the headroom costs nothing.)

## CORRECTION, same day (branch `s11-25-followup-object-bounds`)

**The budget stated above ("under 7 s on this Mac", 6.11 s at 252,491 cells) is wrong by 3x, and the
cell bound alone did not close AUD-004.** Do not quote the 6.11 s figure.

What I got wrong: the STEP 0(b) timing scaled `twostory.json`, which has 5 objects. Scaling it changes
the cell count and holds the object count fixed, so it measured one cost term and concluded that term
was the whole model. It is not.

Blocked-route culprit attribution (`obstructions.py`: `culprit_object_ids`, `_reachable`) re-rasterizes
the room once per candidate object, so cost grows **~O(n^1.7) in the objects ONE room holds**, almost
regardless of its cell count. Measured 2026-09-30, a 3.5 m x 3.5 m room (1,225 cells — *half a percent*
of the cell bound) with objects piled against the only exit, **one** peril:

| objects | 1 peril | | objects | 1 peril |
|---|---|---|---|---|
| 10 | 0.27 s | | 100 | 9.03 s |
| 25 | 0.90 s | | 200 | 42.67 s |
| 50 | 2.79 s | | 400 | 134.17 s |

x3.2 for every x2 objects. The old `MAX_OBJECTS_PER_FLOOR = 500` therefore permitted a **~10-minute
`/score`** while passing every bound this session added — exactly the AUD-004 denial of service the cell
bound was supposed to have closed. AUD-003 makes the bearer token public, so the bound has to hold
against an adversarial body, not merely a realistic one.

**Fixed:** `MAX_OBJECTS_PER_ROOM = 25` (counted with the same bounding-box overlap test
`objects_intersecting` uses, because that is the set the router rasterizes against),
`MAX_OBJECTS_PER_FLOOR` 500 -> 120, `MAX_OBJECTS_TOTAL = 200`. Owner chose 25/room over 40/room when
asked; 25 keeps ~22x headroom over the largest committed fixture (9 objects per floor) and sits well
above RoomPlan's ~5-15 detections per room, so no realistic home is affected.

**The corrected budget is a measured 21.82 s** for a 3-peril `/score` on the COMBINED worst case a valid
home can now reach: 8 floors, 200 rooms, 245,000 cells, 200 objects at 25 per room, every route blocked.
`test_the_maximum_home_stays_inside_the_stated_cost_budget` now pins the bound VALUES that figure was
measured at and fails if any of them changes — deliberately, because the two cost terms are not cleanly
additive and the formula that pretended they were is what produced the wrong 7 s claim.

**The general lesson, and it is the same shape as the 2026-09-24 S11.7 entry in `decisions.md`:** a
scaling experiment that varies one input measures the term that input drives, and says nothing about the
terms it held constant. The fixtures are small in *every* dimension, so any cost model derived by
scaling them is under-determined. Vary each factor independently before claiming a bound is sufficient.

Gate after the correction, 2026-09-30: corpus valid; backend **932 passed, 1 skipped**; EditorCore
**635 passed, 0 failures**; `typecheck-ios.sh` ok on all four targets.
