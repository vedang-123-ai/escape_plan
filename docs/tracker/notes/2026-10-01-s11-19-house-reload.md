**The fix (minimal design, AUD-013's recommendation).** New `Editor/Core/HouseEditorSessionController.swift`
(Foundation-only, in EditorCore): it keeps the `HomeFingerprint` of the file as the session last read or wrote it.
- `appear()` re-arms the open-home guard first, then compares the file: changed → House reloads it, clears undo, and
  shows one line. Called on the first load and on every `onAppear`.
- `save()` (every autosave, undo and redo) compares again first. A changed file is NOT written; House reloads it.
- A file that was on disk and is now missing closes the session for good; autosave never re-creates it. A brand-new
  home (never on disk) is created by its first save as before.
- A file that exists but does not decode is never written over.
- It reaches disk through a 3-method protocol (`HouseEditorDocumentAccess`) and tells the app through
  `HouseEditorRegistration`; the app side is `Screens/HouseEditorSessionController+App.swift`
  (`HomeDocumentStore` conformance and `HouseEditorAppRegistration`, which sets `library.editor` and sync's
  `openHomeID`).
- The trap that shaped it: `HomeDocumentStore.save` stamps `meta.modified`, so the file never equals the in-memory
  model it was written from. The controller fingerprints what landed (re-reads after save), else every own save would
  look like another writer's. Pinned by `testOwnSavesDoNotTriggerAReload` and
  `testTheSessionsOwnSavesAreNotMistakenForAnotherWriter` (real store).

## Decisions / surprises

- **Minimal over structural.** Every writer found (`grep -rn '\.save(model:' escape_plan`: onboarding, HomeScreen's
  re-scan add, sync pulls, Profiles, BuildFromPlan, seeding) writes the file; none needs to share House's live store
  to be caught by a fingerprint check on appear and before each save. Trade-off: a reload clears undo history, and an
  edit made in House while the file changed underneath is not saved (the newer file wins). Both are said in the
  notice. Logged in `docs/decisions.md`.
- **The onboarding interview cannot be the "other writer" in the walk.** It only opens from `ContentView.onAppear` at
  launch, and a relaunch rebuilds House's session from disk, so the stale-session case never arises. The walk used a
  direct edit of the home file from the Mac while the app ran (the same thing a sync pull does), with no debug code.
- **`HomeLibrary.editor` was enough again.** The sync repository's own comment says `openHomeID` exists because House
  used to be built with `library: nil`; since S11.18 there is one library and House gets it. Both are still set, by
  one registration object, on every appear.
