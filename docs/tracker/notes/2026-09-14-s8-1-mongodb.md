Three judgement calls, all in `docs/decisions.md`:

1. **PyMongo async, not Motor.** The playbook says "Motor or Beanie". Motor hit
   **end-of-life 2026-05-14** — four months ago. Building the project's first
   database layer on a dead driver would have been a knowing defect. Verified
   against the installed package, not just docs: `close()` really is a coroutine
   (it is not in Motor), which is the migration's sharpest edge.
2. **Cloud sync is optional.** A missing `MONGODB_URI` disables the layer rather
   than refusing to boot. Fail-closed is right for `BACKEND_BEARER_TOKEN` (an open
   backend is a hole) but wrong here: every pre-S8 endpoint and the entire demo path
   need no database, so fail-closed would have traded a working product for an
   unbuilt feature — and broken all 394 existing tests.
3. **No mongomock, no Docker.** `mongomock` is stale with no 3.13 and no async;
   `mongomock-motor` would drag the EOL driver back in for tests alone;
   Testcontainers makes Docker a precondition for running the suite. A ~30-line stub
   implementing only what `Database` touches keeps the default suite
   infrastructure-free.

## Verified

- Backend **426** not-live pass, 13 deselected (was 394 — the 32 new tests).
- Async tests genuinely execute: proved with a deliberately-failing canary, which
  failed as `[asyncio]`. An async test that is silently never awaited passes.
- Real `AsyncMongoClient` against a dead port → `unreachable` in ~3s, not the 30s
  driver default, and `close()` awaited cleanly.
- App boots, serves `/health`, and shuts down with no `MONGODB_URI` at all.

## NOT verified — the honest gap

The acceptance criterion "backend starts successfully and connects to MongoDB" is met
only in the degraded and stubbed senses above. Logged in `BLOCKERS.md` §4 with the
next action. The `mongo`-marked tests do not exist yet — they should be written with
a server in hand, not guessed at now.
