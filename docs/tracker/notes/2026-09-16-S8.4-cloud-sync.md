## What happened

Built the sync layer in `escape_plan/Sync/` and symlinked the directory into
`tools/editorcore/Sources/EditorCore/Sync`, exactly the way `Auth/` already is. That is the
whole reason this session produced verified work rather than more uncompiled Swift: the
directory is pure Foundation, so `swift test` reaches every line of it on a machine with no
simulator.

Built in the order STEP 0 prescribed — verifiable work first, device-gated UI last:

1. **`CloudHomeModels`** — the `/homes` wire shapes. `id`, never Mongo's `_id`; no `revision`
   field on the request, because the server owns it.
2. **`HomeFingerprint`** — the dirty check. See "the byte trap" below; this is the piece the
   session most easily gets wrong.
3. **`SyncState` + `FileSyncStateStore`** — the sidecar at `<Documents>/sync-state.json`.
4. **`CloudHomesClient`** — `GET`/`POST /homes` with an injected `URLSession`, the same
   dependency-injection trick `AuthClient` uses so the wire contract is testable here.
5. **`SyncReconciler`** — a pure function over (local, remote, sidecar) → a plan. Every
   decision lives here; nothing in it does I/O.
6. **`SyncManager`** — `@Observable`, runs the plan, owns the status the badge renders.
7. **`HomeDocumentSyncRepository`** (app-side) and **`SyncStatusBadge`** (device-gated).

## Decisions / surprises

**The byte trap, and why the fingerprint is taken from the decoded model.** A home that has
been through the server differs from the local one by bytes but not by value — pydantic writes
explicit `null` for absent optionals and fills `objects: []`. So the fingerprint is computed
over a *canonical re-encoding of the decoded `HomeModel`*, never over stored or received bytes.
`HomeFingerprintTests.testAServerRoundTripDoesNotLookLikeAnEdit` pins it against the **real
bytes** the backend emits for `bungalow.json` (generated with `model_dump_json()`, command in
the test's doc comment). Had this been wrong, the app would have re-uploaded the user's entire
library on every sync, forever, with no edit anywhere.

**The JWT goes on `/homes` and nowhere else.** WHAT-TO-ADD #1 says "attach the JWT to all
requests" and that is wrong as written — `/routes`, `/score` and `/chat` are guarded by the
shared `BACKEND_BEARER_TOKEN`, a different axis. `CloudHomesClient` is the only place a JWT is
attached and it can only build `/homes` URLs, so the separation is structural rather than a
convention someone has to remember. `APIClient` is untouched.

**Conflicts: `revision` first, `meta.modified` only as the tiebreak.** `revision` answers "is
the server ahead of what I last saw?" — a monotonic counter the server owns, which is the only
trustworthy signal across two devices whose clocks disagree. It cannot settle a *genuine*
conflict (edited here AND there) because both sides are ahead by construction; only there does
last-write-wins apply. **An exact tie goes to the server**, so two devices reconciling the same
pair reach the same answer instead of each preferring itself and ping-ponging forever.

**Three hazards found while building, each now a test:**

- **The ping-pong.** `HomeDocumentStore.save(model:)` stamps `meta.modified` with the current
  time. A pulled home saved that way looks *newer* than the server's copy, gets pushed straight
  back, the server increments its revision, and two devices trade the same home forever with no
  edit between them. `writePulledHome` passes `now: home.meta.modified` so the pull lands
  verbatim. `testAPulledHomeIsNotImmediatelyPushedBack` is the guard.
- **Duplicate server records.** Two devices that both create the same home before either syncs
  each POST with no `home_id`, so the server mints two records carrying the same embedded
  `home_id`. The backend cannot prevent it (no uniqueness constraint on a field inside the
  document), so the client collapses them — highest revision, then latest `updated_at`, then
  lowest record id — and every device must pick the same winner or they fight.
- **Sync clobbering an open editor.** `writePulledHome` refuses to overwrite the home currently
  open in the editor and surfaces `SyncFailure.editorHasTheHomeOpen`. A home that syncs a
  minute later beats a lost edit.

**Sync state is a sidecar, not a schema field.** Adding `last_synced_revision` to `HomeModel`
would be a `schema_version` bump plus matching pydantic and Swift changes. It is also wrong on
the merits: sync progress is a fact about *this device*, and a device-local fact stored inside a
synced document is overwritten by the very sync it describes. Nothing under `schema/`,
`backend/app/models.py` or `escape_plan/Models/` was touched, so no `schema-contract-guardian`
run is owed.

**A third error type.** `SyncFailure` joins `BackendFailure` and `AuthFailure` for the reason
`AuthFailure` exists: the status codes are shared but the response differs. A 401 here means
"your session expired" and must drop the token and re-authenticate — not "wrong password" and
not "open Settings".
