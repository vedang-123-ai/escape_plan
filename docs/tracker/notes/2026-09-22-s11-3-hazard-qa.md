## Decisions / surprises

**BUG-03 was not a deletion.** The QA note's recommended fix was to skip R1 for unsecured water
heaters. That is correct about which rule wins and wrong about what it costs: R5 has no
geometry, so deleting the R1 finding would have left the user, for that object, the only
finding in the whole engine with no measured number — which spec §2 forbids. R5 now takes R1's
`target`/`reach_m`/`threshold_m` with it. One card, one action, measurement intact.

**BUG-04 could not be fixed by changing the string.** `target` was derived by sniffing the
word `"door"` out of the detail sentence. Renaming the label to "window" would have silently
retargeted the finding to `"sofa"` — in a fixture with no sofa. The target search is now one
function returning the target *kind*, which both R1 and R5 call.

**BUG-02 was never only R1's.** The QA note filed it under R1 because that is where it was
observed, but `room_objects` is shared by all five rules, so R3 bled across walls identically.
There is a test for that now.

**Four for four were logic bugs, not perception failures.** That is the load-bearing argument
in `docs/decisions-object-detection-future.md`: every defect the QA pass found was fixable by
reading the code. None needed a better detector. Fix the reasoning before buying perception.

**The `point_in_poly` helper already existed** — copied inline in three separate functions, and
reachable from none of the loops that needed it. That is *how* BUG-02 happened: the author
reached for a bounding box because the correct helper was not in scope. Hoisted to module
level. Same for `dist_point_poly`, which was being redefined inside a loop body on every
iteration.

**A comment in the code was the author noticing BUG-01 and deciding not to fix it:** *"Wait,
what if they have two heat sources? Let's just trigger for all other objects."*

## What the grounding-auditor caught

Verdict **GROUNDED, no blocking violations**; seven non-blocking findings, all in BLOCKERS. The
one that mattered, and it was mine:

**N1 — R5 had inherited R1's `elevation_m == 0` gate.** So the very fix I wrote to stop BUG-03
costing the user a measured number had its own case of costing them one: an unsecured water
heater on a stand — common in a garage, required outright where the ignition source must be
lifted — emitted a finding with no `target`, no `reach_m` and no `threshold_m`, *with a bed
squarely inside its topple band*. And I had already written that gap into the spec in a
narrower form ("a heater with nothing in reach"), which is what made it look handled. R1's
elevation gate is there to separate floor-standing furniture from a wall shelf (R2's job); a
raised water heater is neither, and it still topples. Fixed with a test, corrected in
`decisions.md` as a row against my own earlier row.

The lesson worth carrying: **the sentence I wrote describing a limitation is what stopped me
looking at it again.** Writing down a known gap is not the same as having measured its edges.

Two findings (N3, N4) are real and deliberately not fixed here — N3 is `backend/app/ai/`,
which CLAUDE.md reserves for S11.4, and N4 is a contract question about which field carries R2's
measured elevation, not one of this session's four bugs. Both are in BLOCKERS with owners.
