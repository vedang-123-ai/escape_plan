# S11.27 — AI spend has a ceiling that nobody outside the server can reset

- **Who:** P3 (agent-run)
- **Date(s):** 2026-10-03
- **Status when I stopped:** done and merged. AUD-003 mitigated (not eliminated — the token stays public by
  design), AUD-006 fixed, AUD-043 fixed.

## What happened

The premise first, because the rest only makes sense from it: **the bearer token is public.** It ships in
plain JSON inside every app build, so anyone with the IPA has it. It identifies the app, not the caller. It
stops the service being an open relay for anonymous traffic and it bounds nobody's spend. That is now written
into `docs/decisions.md` and into `require_token`'s own docstring, with an explicit "no effort will be made to
hide it in the bundle" — obfuscating a secret that must be on the device buys nothing against `strings`, and
pretending otherwise is how the real control never gets built.

**The ceiling** is a global daily AI budget: `AI_DAILY_CALL_BUDGET` (default 300) calls per UTC day,
server-wide, 429 with a `Retry-After` that points at UTC midnight rather than five seconds away. It counts
every AI call whoever makes it, which is the only shape of limit a holder of a public token cannot reset — a
per-client bucket is per-client however cleverly it is keyed. `/health` reports remaining and spent, numbers
only.

**The per-client key was the more interesting bug.** It was the *first* `X-Forwarded-For` hop, which the
caller writes, so a script got a fresh bucket per request by varying a header: the limiter bounded nobody.
Render's own FastAPI guidance calls trusting that value "a critical vulnerability, allowing bad actors to
spoof their IP address", and their docs confirm "all inbound traffic to Render web services passes through
Cloudflare's global network" with proxies **appending** — so the trustworthy entries are on the *right*.
`client_key` now prefers `CF-Connecting-IP` (Cloudflare overwrites it per request), else counts in from the
right by `AI_TRUSTED_PROXY_HOPS`, else the socket peer. Both configurable so no vendor detail is load-bearing;
`AI_TRUSTED_PROXY_HOPS=0` is the local no-proxy setting.

**AUD-006** — `/score?include_recommendations=true` was the one AI call site outside the guard. It could not
take `AI_GUARDS` as route dependencies: `/score` is deterministic and the demo path leans on it, so budgeting
the whole route would throttle the thing that still works when the AI is down, which is the separation the
project rests on. The guards run imperatively for the flagged branch instead, through the *same* enforcement
functions — one implementation, not two, since two is how this drifted.

**AUD-043** — `require_token` was duplicated because importing it from `main` into the router closed a cycle.
Both it and `AI_GUARDS` now live in `app/deps.py`, which imports neither. `grep -rn "def require_token"
backend/app` returns exactly one hit.

**Evidence (2026-10-03).** `backend/.venv/bin/python -m pytest backend/tests/ -m "not live"` →
**998 passed, 1 skipped, 29 deselected** (54 s), up from 973. `test_route_guards.py`: 31 passed.
`grep -rn "def require_token" backend/app` → 1. `python3 backend/corpus/validate.py` → valid.

## Decisions / surprises

**One test asserted the vulnerability.** `test_client_key_prefers_the_first_forwarded_hop` was green and
pinned exactly the behaviour that let a caller choose their own rate-limit bucket. Deleting a passing test
feels wrong until you read what it guarantees; this one guaranteed the hole. Replaced with six tests, the
load-bearing one being `test_a_forged_forwarded_chain_cannot_win_a_fresh_bucket` — nineteen forged chains, one
resulting key.

**The budget is charged on entry, not on success.** A call that reached Anthropic and then failed has usually
already cost credit, so refunding failures would let a loop of failing calls run unbounded — which is the
precise shape of the incident that drained the account. There is a test pinning that a 502 still debits.

**It counts calls, not tokens, and that is a real limitation.** Debiting actual `response.usage` needs every
AI module to report it back, and `backend/app/ai/` is outside this session's OWNED FILES. Every call site has
its own `max_tokens` so a call count does bound spend, but a run of long calls costs more than a run of short
ones and the budget cannot tell them apart. BLOCKERS line; **S11.29** is the next session working inside
`app/ai/` and should thread usage back while it is there.

**A restart resets the counter.** In memory and per process. Accepted and documented rather than persisted in
Mongo: attaching spend control to a database the demo trim is actively switching off would make the control
depend on a feature being removed.

**Two things in the session file have been overtaken by the trim.** It says S11.27 "blocks S11.28" and that
S11.28 "reuses your client-key helper" — S11.28 was dropped on 2026-10-02 when accounts were cut. S11.27 still
blocks S11.29 and S11.39, which is the part that matters.

**App Attest is recorded, not built.** Per-install tokens attested to Apple are the real fix for AUD-003 and
do not fit before Oct 24 — entitlement, server-side verifier, credential store, rotation, and an offline story
for a device that cannot reach Apple, all landing in the iOS networking layer mid-trim. The budget caps the
damage; it does not attribute or revoke per device. Written down so it is a known limitation rather than an
oversight a judge finds.
