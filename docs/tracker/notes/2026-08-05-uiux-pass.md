## What happened

Anish asked for the whole remaining UI/UX list, with one constraint: everything must match the
pure white theme. That constraint turned out to be the substance of the work, not a finish on it.

### The finding: chrome was breaking the model's one rule

The dollhouse's governing rule is that the escape route is the only hot colour in the frame. A
grep for `.orange` found it in **seven screens** — scan fallback warnings, the rejected-edit
line, onboarding hints, the Settings status dot, the AssistantScreen error banner, the drill
screen, and the mid band of the score ring. So route-orange and warning-orange could appear in
the same scroll with nothing telling the user they meant different things.

`Screens/Theme.swift` now owns the semantic scale and chrome contains no route orange at all.
Advisories use `Theme.caution` (#B45309) — a dark amber that reads as ink, not as a lit line.
`Theme.routeInk`/`exitInk` exist only for legends labelling an actual route or exit. 22 call
sites swept.

## Decisions / surprises

All promoted to `docs/decisions.md`. `tools-used.md` unchanged — **no new dependencies**;
everything is SceneKit, CoreGraphics and SwiftUI already in use.

**I rejected part of the design handoff.** It specified one route colour per household member.
Three or four saturated hues is exactly the problem the White Model overhaul removed, and they
would compete directly with the route and the exit green. The figures are white like everything
else; identity is a name pill; the *selected* person's figure takes the accent green. Whose
route is on screen is answered by selecting the person, not by memorising a colour key. If Anish
wants the original, it is a one-line palette change in `PersonFixture` — but I'd argue against it.

**Surprise 1 — thumbnails looked like static.** The first render had visible speckling across
every wall face. Shadow acne: at ~74×54 pt the shadow map samples far below its own texel
density. Turning shadows and SSAO off for tiles (and giving ambient the shadow's share) fixed it
completely. Screenshot before/after confirmed on the simulator.

**Surprise 2 — the preflight script called a healthy backend dead.** `CERTIFICATE_VERIFY_FAILED`
against a service that was fine: python.org builds on macOS ship without a usable trust store.
Fixed in the earlier session's script; noting it here because it will bite anyone running it on
a fresh machine.

**Surprise 3 — six error ladders, all different.** I expected to add a 502/503 branch. What was
actually there was six screens each hand-rolling status-code handling, disagreeing on 401, and
all six offering Retry unconditionally — including for failures where retrying provably cannot
help. The classifier was the fix; the 502/503 split fell out of it.

**Not surprising but worth recording:** SourceKit produced phantom errors continuously
("No such module 'UIKit'", "Cannot find type 'HomeModel'"). Every real error came from
`xcodebuild`. The CLAUDE.md warning is accurate and load-bearing.
