## What happened

**The fix (`escape_plan/Screens/ReadinessStore.swift`).**
1. One cancellable task. `startScoreFetch` is the only way to `/score`: `load` (so launch, `select`, onboarding, sync,
   pull to refresh and House's autosave), `rescore` (Retry, Score's refresh, a household change) and `toggleDone`. It
   cancels the previous request first. `load` awaits the task, so pull to refresh still spins until the answer.
2. Tagged answers. Each request carries its home and a generation number. `finishScore` drops an answer whose
   generation is stale (it was cancelled or replaced), or whose home is no longer active, or that arrives for a home
   that became a draft (S11.17's guard). Success and failure are treated alike.
3. `breakdown` is computed from a stored `(homeID, breakdown)` pair and is nil for any other home, so A's score cannot
   show under B's name even if a caller forgets to cancel.
4. `isScoring` is set by the request that starts and cleared only by the current request finishing, or by a cancel
   that starts nothing new.
5. A cancelled request (`CancellationError` or `URLError(.cancelled)`) changes no state and shows no failure.
6. `switchActiveHome` (the only place the id changes after launch, used by `select` and `ensureActiveHome`) cancels
   the request and clears the previous home's score and failure notice.
7. `toggleDone` ignores an item that is not on the active home's checklist. `replaceActiveHome` ignores a model for
   another home.
8. `clearScoreForDraft` deletes the draft-era cache with the new `ScoreCache.remove(homeID:)` (the S11.17 hand-off;
   owned-files exception in `docs/decisions.md`).

**Tests (`escape_planTests/ReadinessStoreTests.swift`).** `GatedScoreProtocol` holds every `/score` until the test
answers it and reads the home id from the request body, so a test decides the order answers arrive in. Answers are
delivered on the protocol's own thread so a cancel and an answer cannot interleave. New tests:
- `testPreviousHomesLateScoreNeverLandsOnTheNewHome`: A in flight, switch to B, B answers 40, then A answers 90. B's
  40 and B's checklist stay; the cache holds 40 for B and nothing for A.
- `testPreviousHomesFailureAfterSwitchingShowsNothing`: A answers 503 after the switch. No failure, spinner still on
  for B.
- `testSupersededRequestShowsNoFailureAndKeepsTheSpinner`: two rescores; the first is cancelled. No failure, spinner on,
  score unchanged until the second answers.
- `testCancellationIsRecognisedInBothForms`.
- `testTickingAnotherHomesItemChangesNothing` (plus the control: B's own item ticks, saves under B, re-scores B).
- `testReplacingWithAnotherHomesModelIsIgnored`.
- `testRescoreBeforeTheNewHomeIsLoadedSendsNothing` (from the review).
- `testScoreCachedBeforeTheFixIsNotShownForADraft` now also asserts the cache file is gone.

## Decisions / surprises

- The playbook file is kept, like S11.15 to S11.22 (decisions.md).
- `ScoreBreakdown` does carry a `home_id` from the server, but the store tags the answer with the home it sent instead,
  so the check does not depend on the server echoing the id.
- House's autosave calls `load`, so continuous editing during a slow cold start keeps replacing the request; the score
  lands once editing pauses. Arguably correct (the old answer was for the old model).
