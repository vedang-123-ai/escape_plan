Method: code walk of every screen reachable from `ContentView`'s five tabs, plus the 2026-09-28 simulator suite (UI

### [AUD-027] "Share with fire department" in Settings packages the most-recently-modified home, not the active one, and fails silently

**Severity:** P2
**Location:** `escape_plan/Screens/SettingsScreen.swift:238-261` (`generateSnapshot`): `store.list().first` = newest
`meta.modified`; every failure is `guard … else { return }` or `print("Failed to generate snapshot: …")`.
The Tasks-tab card (`TasksScreen.swift:292`, `ShareWithFireDepartmentCard(homeID: home.id, …)`) uses the active home
correctly.
**Category:** UX / privacy
**What I found:** Two entry points to the same feature pick different homes. The newest-modified home changes whenever
any home is saved — a sync pull, a demo home touched in House, a blank "New Home" (AUD-021).
**Current behavior:** From Settings, a user with several homes can hand a fire department the floor plan and occupant
information of a *different* home than the one they are looking at. If the store, preview or write fails, the spinner
stops and nothing appears.
**Expected behavior:** Settings uses `readiness.activeHomeID` (or asks which home), names the home in the consent sheet,
and shows an error on failure.
**Why this matters:** The package contains vulnerable-occupant information by room; sending the wrong one is a privacy
error with real-world consequences.
**Evidence:** Code reading of both call sites.
**Potential fix direction:** Remove the Settings share button and link to the Tasks card, or inject `ReadinessStore`.
**Dependencies / considerations:** `ShareWithFireDepartmentCard` already has the right shape — reuse it.

### [AUD-029] A failed room re-check is reported as a score failure, and its Retry button re-imports the wrong scan or does nothing

**Severity:** P2
**Location:** `escape_plan/Screens/HomeScreen.swift:459-473` (`processRecheck` → `BackendFailure(error, while: .score)`),
`:475-492` (`importScan` sets `lastScanArtifacts`), `:494-520` (banner Retry → `retryScanImport()` → `importScan(lastScanArtifacts)`)
**Category:** UX / error handling
**What I found:** Re-check (partial re-scan) shares the full-scan failure banner, but not its retry state. It never sets
`lastScanArtifacts` and it labels its error as the score.
**Current behavior:** A re-check that fails on `/convert` or `/diff_obstructions` shows "Getting your preparedness score
needs a connection…". Tapping Retry either does nothing (no `lastScanArtifacts`) or, if an earlier full-scan import
failed and was not dismissed, **imports that old scan as a brand-new home**.
**Expected behavior:** A `.scanConversion`-labelled failure with a retry that re-runs `processRecheck` for the same
artifacts and room.
**Evidence:** Code reading.
**Potential fix direction:** Store `(artifacts, roomID?)` as the pending retry; branch in `retryScanImport`.

### [AUD-049] Silent failures on user actions

**Severity:** P3
**Location:**
- `HomeScreen.swift:89` — `try? library.store.save(model: home)` after "Add to Home"
- `SettingsScreen.swift:243-260` — snapshot generation (AUD-027)
- `AssistantScreen.swift:392-394` — `try? store?.save(...)` for the conversation (the screen does have a separate
  "history can't be saved" note when the store itself is nil, per audit B1)
- `escape_planApp.swift:66-71` — starter-home seeding failure only `print`s
- `DiffReviewSheet` "Add to Home" gives no confirmation that the object was saved
**Category:** UX
**What I found / current behavior:** Each of these can fail with no feedback; the UI then states or implies success.
**Expected behavior:** Every user-initiated write either succeeds visibly or shows the shared `BackendFailureBanner` /
an inline error.
**Evidence:** `grep -rn "try? " escape_plan/Screens` and code reading.
**Potential fix direction:** Replace `try?` on user-initiated writes with `do/catch` into the screen's existing error state.
